# 决策与行动轨迹

## Corpus / method

### 研究问题

本维度研究的不是“他说自己如何决策”，而是五类行为痕迹中反复出现的选择：何时拆分、何时继续、何时停止、什么动作必须人工批准、什么证据足以称为完成，以及重复问题何时被转化为工具或规则。

### 归因与隐私处理

- 三个 Git 署名被视为同一人的稳定别名；作者字段只证明提交归因，不证明每行代码均由本人手写。
- 240 条评论虽由本人账号发布，但其中至少 18 条明确标记为 AI、子代理或任务系统生成；这类文本仅作为“采用了何种流程”的证据，不作为个人措辞或独立判断的直接证据。
- 会话索引几乎只保存任务入口：1,743/1,744 条首尾用户消息相同，因此不能从索引还原结果、转折或最终决定。大量 automation/system wrapper 也会放大工具化语言。
- 原始会话索引包含高敏自由文本。研究过程不复制任何原文、内部地址、事项编号、项目/人员标识、客户数据、凭据或原始日志；下方仅保留匿名聚合和可复算计数。

## Decision heuristics

### H1. 先固定事实源、owner 与契约，再开始改动

面对跨服务或数据链路问题，常见起手式是先确认 canonical source、owner repo、输入输出契约、版本和消费者边界。若根因尚未归属，倾向继续调查或转为 `needs-info`，而不是凭报错位置直接修改最显眼的服务。

- 行为信号：评论样本反复先写“当前事实/边界/未知”，再给实施建议；跨服务事项常显式区分 source、runtime 与 deployment owner。
- 决策意义：优先降低“修错层”和局部修复破坏集成契约的风险。
- 置信度：**高**。GitLab 事项、评论和控制面提交三源一致。

### H2. 按可逆性和验证边界拆解，而不是只按组件拆解

常见拆法是：契约/基线、实现、离线验证、低风险环境验证、生产或数据面动作、回滚/结项。会把导入与切换、源码与部署、实现与真实验收拆成可独立审计的步骤；未通过前一门禁时，后一步保持阻塞。

- 行为信号：134 个关闭事项中 30 个带原生子任务；风险较高事项经常把真实环境动作保留给人工门或后续任务。
- 决策意义：拆分单元由“谁能独立证明安全”决定，而非代码目录决定。
- 置信度：**高**。事项结构和评论中的执行顺序高度一致。

### H3. 先做固定基线和有界样本，再渐进扩量

偏好固定版本、固定输入、同批配对、先小样本再扩大。对数据导入、provider-live、回放和生产验证，通常先 dry-run 或非生产环境，再用小批量、单次授权或固定比例做 canary；写后复查或同样本重跑用于确认幂等和回归。

- 行为信号：评论中持续出现 exact revision、固定 cohort、paired comparison、预算/次数上限、渐进扩样和写后复核。
- 决策意义：把“看起来改善”转成可比较的增量证据，同时限制成本与爆炸半径。
- 置信度：**高**。多个不同工作类型中重复出现。

### H4. 没有正确性证据时，不用吞吐或召回单指标替代结论

聚合指标改善不足以触发发布；还要求 owner/intent、有效性、可靠性或人工 judge 等正确性门。若样本不可回放、对照不等价、provider 不稳定或收益不能复现，结论会降级为 baseline / inconclusive / no-go，而不是把实验包装成成功。

- 行为信号：关闭事项中有 17 个 `wontfix`，且多条评论明确保留默认关闭、拒绝扩大样本或拒绝上线收益未证实的方案。
- 决策意义：允许“完成调查但不发布”成为合法成果。
- 置信度：**高**。事项标签、实验评论和关闭语义互相印证。

### H5. “完成”是分层证明，不等于代码已写或 MR 已开

稳定的完成定义包含四层：实现已进入 canonical 主线；精确版本的必需流水线/测试通过；需要时已有对应环境的真实证据；剩余风险、未做动作和后续 owner 被明确记录。部分实现、绿色单测或已部署中的任一层都不能单独替代全链路闭环。

- 行为信号：240 条本人评论中，177 条命中版本/流水线/测试/证据语言，196 条命中完成或关闭语言；两者经常同段出现。
- 决策意义：完成判定绑定 provenance，减少“测的不是发的版本”。
- 置信度：**高**。评论和事项验收字段直接支持。

### H6. 高风险动作默认 fail-closed，授权是一次性且窄范围的

生产、真实数据写入、alias/流量切换、权限、凭据、付费 provider 和不可逆删除不会从“允许调查”自动推导为“允许执行”。授权常被限定为环境、对象、次数、样本和时间窗；失败后不自动扩大或重试。

- 行为信号：134 个事项中 76 个涉及风险表面，53 个出现隐私/安全边界；评论全量中 69 条命中授权、脱敏、未执行或禁止 mutation 的语言。
- 决策意义：把权限范围当作运行时输入，而不是一次性的口头背景。
- 置信度：**高**。跨生产、权限、数据和 provider 场景一致。

### H7. 重复两次以上的摩擦，倾向沉淀成 skill、doctor、validator 或 automation

遇到重复的收尾、环境漂移、仓库发现、验证、清理、报告和监控工作，常把做法写成可发现入口、脚本、契约测试或周期任务，而不仅是写一次文档。提交样本中工具/功能、维护、知识沉淀占主体；会话索引中约半数以上带 agent/tool/workflow 语言，虽受自动任务模板放大，方向仍明确。

- 行为信号：739 条明确归因提交候选中，浅层分类得到知识沉淀 296、功能/工具 113、维护 120；会话索引有 159 条使用子代理，共记录 990 个子代理实例。
- 决策意义：优化目标不只是当前 ticket 的吞吐，还包括下一次处理的边际成本。
- 置信度：**中高**。提交证据强，会话索引受自动化污染。

### H8. 偏好可恢复、可审计的默认值

常见选择包括稳定 ID、checkpoint、幂等、默认关闭、保留旧目标、先准备回滚、把运行产物放在仓库外、日志只存低敏分类，以及用 source-of-truth 消除手工漂移。发生故障后，除了修当前问题，还会补防复发规则和诊断入口。

- 行为信号：评论样本在数据处理、发布、主机故障、配置和观察者权限等不同场景重复出现这些选择。
- 决策意义：把失败设计成“可定位、可停止、可恢复”，而非只追求成功路径。
- 置信度：**高**。跨域复现，且提交中有对应工具化轨迹。

## Execution loop

观察到的典型执行循环可压缩为：

1. **界定**：确认真实 owner、canonical source、消费者、环境、权限边界与哪些事实仍未知。
2. **写清 done condition**：把业务结果、质量门、真实环境证据、隐私要求和明确不做项写入事项。
3. **按风险拆包**：把可离线完成的契约/实现与需要真实数据、付费调用、生产权限的动作分离；建立阻塞顺序。
4. **固定基线**：钉住版本、样本、配置、时间窗、统计口径和成本预算；先重现，再改代码。
5. **隔离实现**：使用独立分支/worktree，做最小 owner-repo 改动；为 bug 增加复现与相邻回归覆盖。
6. **逐层验证**：focused test -> 全量/静态门 -> 精确版本流水线 -> 非生产运行 -> 经授权的有界真实验证。
7. **比较并决策**：同样本配对，区分 correctness、recall、latency、cost 与 reliability；结论可以是 ship、hold、no-go 或 needs-info。
8. **持久化收尾**：合入 canonical 主线，记录 provenance、已做/未做动作、残余风险和下一 owner；重复流程再沉淀为工具或 automation。

这个循环不是严格线性的。真实证据可能暴露基线口径错误或新的独立故障，届时会回到“界定/拆包”，并将新问题分离，避免让已完成的修复无限保持模糊。

## Risk / quality gates

| Gate | 触发条件 | 通过条件 | 未通过时的典型动作 | 置信度 |
| --- | --- | --- | --- | --- |
| Ownership / contract gate | 跨服务、API/SSE/schema、数据链路 | provider、consumer、事实源和兼容边界明确 | 调查、转 owner、`needs-info`；不先改显眼层 | 高 |
| Privacy / secret gate | 生产日志、客户/联系人数据、凭据、自由文本 | 只留脱敏聚合、匿名指纹或受控 evidence reference | 停止持久化原文；限制样本或改用公开/合成数据 | 高 |
| Source quality gate | 任何非平凡代码变更 | 复现测试、相邻回归、lint/typecheck/coverage 和精确 SHA pipeline 满足仓库契约 | 不调低门槛；区分本次回归与主线既有失败 | 高 |
| Runtime provenance gate | 部署、回放、性能或线上结论 | 实际运行版本可追溯到已审查源码和配置，环境健康且前后状态记录完整 | 只记 baseline，不宣称发布/修复完成 | 高 |
| Authorization gate | 生产、数据写入、权限、付费调用、删除或流量切换 | 明确到环境、对象、次数/预算、时间窗的当前授权 | 保持 `ready-for-human`；不把读权限扩大为写权限 | 高 |
| Outcome gate | 实验、质量提升、召回优化 | 固定样本、等价对照、正确性门和可复现收益均通过 | 默认关闭、no-go、缩小结论或请求新证据 | 高 |
| Reversibility gate | alias、发布、主机/内核、批量导入 | 回滚目标/命令已准备，先小批量或 dry-run，旧状态不被提前删除 | 暂停 apply，先恢复路径或补 runbook | 高 |

## Delegation / automation

### 委派模式

- 委派集中在适合并行搜索、评审或独立验证的任务，而核心风险决定仍回收到 owner gate。1,744 个会话索引中 159 个带子代理（9.1%），共 990 个子代理实例，说明不是“每个任务都并行”，而是少数复杂任务高密度扇出。
- 子代理/AI 产出的文字会被明确标记，最终评论仍强调范围、未授权动作和剩余人工门。这个模式更像“并行取证 + 中央决策”，而非完全自治。
- 事项层偏好原生父子层级；但个人任务系统中 73 条任务的 `subtask_count` 全为 0，说明正式工程分解主要发生在 GitLab/Harness，而不是飞书任务。

### 自动化倾向

- 自动化对象集中在高频但可规则化的工作：环境自检、仓库/skill 发现、工作树与存储清理、issue 对账、日报周报、验证、监控和发布证据。
- 自动化仍受 fail-closed 约束：对外发送、生产 mutation、权限变更和付费调用需要显式范围；自动流程应报告 blocker，而不是静默绕过。
- 更偏好“工具 + 文档 + 契约测试”的三件套。只写说明不足以防漂移；只写脚本又缺少发现入口和边界。

## Observed divergences

### D1. 强调先建可追踪事项，但实际存在明显事后补录

134 个已关闭事项中，至少 39 个命中“历史补录/此前已完成/retrospective”模式；7 月和 8 月还出现批量对账式补票。真实行为常是先完成工作，再通过周度/会话审计补齐 tracker。

- 解读：并非不重视追踪，而是执行吞吐高于即时记录能力，随后用 reconciliation 偿还可追踪性债务。
- 风险：创建时间不再代表决策发生时间，周报和 lead time 会失真。
- 置信度：**高**。

### D2. 口头上的“闭环”很严格，但关闭状态本身语义混杂

全量都是 closed，但启发式关闭语义中仅 56 个属于“已交付或普通关闭”，另有 45 个仍带阻塞/未完成信号、16 个处于人工门、17 个为 `wontfix`。关闭有时代表完成，有时代表去重、过时、no-go、改走人工或范围终止。

- 解读：他的真实 done definition 严格，但 tracker 的 closed 状态不能单独承载该定义；必须读取标签和 closing evidence。
- 风险：基于状态的自动报告会把 no-go、人工作业或未完成子项误算成交付。
- 置信度：**高**。

### D3. 工程分解成熟，但个人任务清单仍偏平且有积压

飞书 73 条任务中 46 done、27 todo，全部显示 0 个子任务；部分任务标题仅是链接、提醒、follow-up 或宽泛主题，且有多条跨月才关闭。与 GitLab 中详细的验收矩阵和父子依赖形成反差。

- 解读：飞书更像低摩擦 inbox/提醒层，GitLab 才是复杂工作的执行系统。
- 风险：若工作没有及时迁移到正式 tracker，就容易失去 owner、优先级和完成标准。
- 置信度：**高**。

### D4. 强隐私规范与原始会话捕获之间存在结构性冲突

评论中频繁要求脱敏、低敏日志和受控证据，但会话索引的自由文本仍可能包含内部地址、客户上下文甚至 secret-like material。研究过程已发现这种风险并完全排除原文。

- 解读：安全意识体现在交付物和日志设计中，但入口层的即时粘贴行为仍会把敏感信息带入本地历史。
- 风险：后续搜索、备份、训练或研究若把 session index 当普通文本处理，会扩大暴露面。
- 置信度：**高**；只陈述是否存在，不保留任何值或定位信息。

### D5. 追求自动化和并行，但多数会话仍是单代理、结果不可观测

仅 159/1,744 个索引记录子代理；1,743 条首尾用户消息相同，无法从索引确认自动化是否真正完成。工具化语言的高占比有一部分来自周期任务模板，而非每次都做了新的决策。

- 解读：自动化能力建设很强，但“会话被创建”不等于“工作被可靠完成”；最终证据仍要回到 tracker、Git 和运行环境。
- 风险：用 session 数或 token 数衡量产出会严重失真。
- 置信度：**中高**。

## Failure modes

1. **把 closed 当 done**：忽略 `wontfix`、人工门、去重或残余阻塞，导致完成率虚高。
2. **先做后补票**：丢失真实起始时间、原始假设和中间否决理由，事后材料更容易受结果偏差影响。
3. **聚合指标替代正确性**：found rate、吞吐或绿色 pipeline 改善，却未证明 owner/intent、数据有效性或部署版本一致。
4. **样本和可回放性偏差**：历史请求体缺失、provider 波动、时间窗不同或小样本幸运命中，使结果不能外推。
5. **自动生成文本被误认作本人判断**：评论作者字段相同，但部分内容来自 AI/子代理；语言风格证据尤其容易污染。
6. **工具层膨胀**：skill、router、文档和 automation 快速增加后，需要持续清理、分层发现与契约测试，否则“为降摩擦而建的工具”本身成为摩擦。
7. **入口泄密**：即时粘贴到会话的敏感内容绕过了最终交付物的脱敏规范。
8. **人工门悬挂**：源码已完成但真实验收需要授权或业务 owner，若没有独立 frontier 和提醒，会长期处于“技术上完成、系统上未闭环”。

## Confidence / limits

- **总体置信度：中高。** 最强证据来自 GitLab 事项结构、本人评论和明确归因的主分支提交；三者对风险门、验证习惯和工具化倾向相互印证。
- **成功率不可估计。** GitLab 语料只包含已关闭事项，缺少同时间窗内全部 open/abandoned 项；closed 的语义又不等于成功。
- **提交不是决策全过程。** 主分支记录保留了最终落点，通常看不到被否决方案、讨论和未提交实验；作者别名归因也不能区分本人手写、AI 辅助和他人协作。
- **评论不是纯个人语言。** 至少 18/240 条带明确 AI/子代理痕迹，其他未标记的辅助生成无法排除，因此本报告只推断稳定行为模式，不仿写措辞。
- **飞书任务是偏置样本。** 73 条任务混合 inbox、链接、提醒和工程任务，缺少优先级/依赖的统一结构；不能用它单独评价执行纪律。
- **会话索引只适合统计意图表面。** 它不含助手结果，且 automation/system wrappers 很多；token、模型、session 数和关键词都不是产出指标。
