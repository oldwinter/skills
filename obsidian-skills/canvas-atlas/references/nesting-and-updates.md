# 多图与维护

## 原生导航

总览使用文本卡片概括子系统，再放到子 Canvas 的明确链接。需要文件预览时使用 file 节点，但不要依靠缩略预览传达主结论。

例如文件实际位于 vault 的 `Atlas/Canvas/项目地图/扫描.canvas`，引用必须写完整 vault 相对路径。`扫描.canvas` 不是相对于父 Canvas 所在文件夹解析的 file 路径。

子图提供普通 wikilink 返回父图。不要把父图再作为 file 节点嵌入子图，防止形成递归嵌入。不同视角之间使用普通导航链接。

JSON Canvas 的边引用当前文件内的节点。跨图业务关系在父图画到子系统入口，并在子图说明输入输出；不要把另一文件的节点 ID 直接当作本图端点。

## 可选 Portal

[Advanced Canvas 的 Portals](https://github.com/Developer-Mike/obsidian-advanced-canvas#portals) 支持将其他 Canvas 展开到当前图中。

用户要求 Portal 且插件已启用时，先检查安装版本和实际保存格式。优先通过插件 UI 把已有子 Canvas 文件卡转换为 Portal，再读取结果。不要猜测扩展字段，也不要自动安装或启用插件。目标 vault 禁止未知字段时，仍使用原生模式，除非用户明确授权该扩展格式。

保留文字子图入口作为导航降级。实测展开、打开原始子图、返回父图和重新打开后的保存效果。不能因为插件已安装就宣称 Portal 验收完成。

## 维护边界

首次生成时在导读中记录来源版本和范围，不写“自动保持最新”。更新时重新读取实际来源。

将现有 Canvas 本身作为可编辑真源。不要另建一份永久 graph.json 再覆盖用户画布。语义分析中间表可以是临时工作文件。

已有节点中混合人工与 AI 内容时，修改有明确来源支持且属于本轮范围的部分；保留其他正文。无法区分则生成修订建议，不覆盖整张卡片。

更新验证至少包含一个人工移动并批注的节点。记录它在更新前后的 ID、坐标、尺寸、批注和连线，证明不相关内容没有变化。布局不变但来源已经过期的节点仍应报告。

## 验收任务

验证 Skill 行为时，选实际任务，而非只检查关键词：

1. 给出一个陌生小仓库，要求单文件地图。检查图是否解释运行链，有源文件依据，且没有无用子图。
2. 给出跨模块系统，要求总览与子图。检查父图独立可读、子图新增信息、路径正确、无嵌入环。
3. 人工移动一个节点并加批注，再要求更新另一模块。检查原 ID、布局和批注保留。
4. 给出一个来源不足的关系。检查是否明确待核实，而非生成确定性调用边。
