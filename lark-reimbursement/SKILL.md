# 飞书报销提单

把每一笔报销关联到原始凭证，完成用户授权的创建或提交，并取得可回读的审批实例。本文负责报销核对；通用命令、控件结构和权限处理复用已安装的 `lark-doc`、`lark-approval`、`lark-shared`，按当前阶段读取。

## 0. 先采购审批，再采购和报销

每次开始采购类报销时，先提醒用户：**先创建采购申请单，审批同意后才能采购；采购完成后，才能通过费用报销单申请报销。** 同一任务已核验的环节无需反复提醒。

采购申请入口从用户当前提供的信息或本机私有配置读取：$XDG_CONFIG_HOME/lark-reimbursement/config.json（未设置时使用 ~/.config/lark-reimbursement/config.json）的 procurement_application_url。没有入口时先搜索当前租户可发起的采购审批定义；仍不能确定时询问用户。打开后核对应用和审批定义，链接本身不代表已经创建或批准采购单。租户专属链接保存在私有配置，不写入公开技能源码。

- 尚未采购：先准备采购申请。用户授权发起时使用 `lark-approval` 创建；取得审批同意的实例证据后，才进入采购阶段。报销任务不自动授权付款。
- 已采购、准备报销：获取对应采购申请实例，核对状态为 `APPROVED`、批准时间早于采购时间，以及公司、项目、数量和金额范围覆盖本次费用。新增账号或超出已批范围的采购需单独核对覆盖情况。
- 缺少采购单、仍待审批、被拒绝，或先采购后补批：明确说明缺口，继续整理凭证与草稿；取得合规的采购审批或有权限人员确认的例外处理依据后再提交报销。补单不能表述成事前已批准。

完成条件：采购审批依据可回读、覆盖本次费用，且具备可关联的实例 code；例外处理有明确来源。此项是采购类报销的前置条件，不因表单将“关联审批”设为选填而省略。

## 1. 建立凭证台账

读取来源文档的最新正文及资源引用，保存完整响应到本机私有任务目录。逐项记录：费用用途、数量、币种、申请金额、付款日期、开票日期、证据来源和对应附件。

- 下载原始图片与 PDF，金额和日期以实际凭证核对。图片 alt、OCR 和文档标题只用于定位；存在冲突时看原图或 PDF 页面。
- 金额使用十进制定点计算。区分商品标价、实际付款和退款；已退款订单与截图中的历史交易只作说明，不叠加报销。外币报销使用有依据的结算或汇率口径。
- 分开保存付款日、开票日和申请日。按目标字段语义取值；字段只有“日期”时说明拟用口径。若要求付款日而凭证只有“今天／几天前”，且截图日期不明，询问缺失日期，继续准备其他材料。
- 在任何上传前检查卡密、令牌及无关隐私。优先选能证明同一笔费用且不含秘密的付款凭证；需要遮盖时保留原件、明确标注遮盖内容，金额、日期与交易身份保持可核验。

完成条件：每笔金额有来源，退款处理明确；附件已逐份归属费用；缺失或冲突有明确记录。凭证阶段仅因必填值或金额真实性缺口阻断，采购审批前置条件仍独立适用。

## 2. 映射当前审批表单

按 `lark-approval` 搜索可发起定义并读取详情；已知定义 code 时直接读取。用实时定义获取控件 ID、选项、必填项及节点要求。

- 公司由凭证抬头和用户需求确定；付款账号只能选定义中与目标公司对应的选项。存在多个可行选项时让用户选择。
- 每项费用映射到明细行，汇总金额等于明细金额之和。备注解释采购用途、退款、无发票及日期口径，并保留来源文档链接。
- 查询同一审批定义下已发起的相关单据，完整翻页并比较费用与凭证，识别重复报销。使用时间筛选时同时提供开始与结束时间。
- 将已核验的采购申请实例填入“关联审批”控件；没有该控件时在备注记录采购单链接与编号。指定审批人按当前定义与用户要求填写。三方定义或 API 不支持的必填控件转到对应客户端流程，保留已准备材料。

完成条件：所有必填值有来源，当前定义与请求匹配，没有未解决的重复提单疑点。

## 3. 上传审批附件

需要把本地凭证转换成审批 file code 时，读取 [审批附件上传与验收](references/approval-attachments.md)。该参考补充通用 `lark-approval` 的上传能力空白。

完成条件：每份拟提交附件都有本地文件、用途、摘要校验值、远端 file code 和上传回执；上传结果保存在本机私有目录，可在恢复任务时复用。

## 4. 创建或恢复申请

准备可审阅的公司、付款账号、金额明细、日期口径、附件数量和节点参数；遵循本次会话已有授权与运行环境的确认要求。用户只要求草稿时停在草稿；已明确授权创建或提交且关键值无歧义时执行同范围操作。

按当前控件参考组装 `form` 的 JSON 数组字符串，生成并保存一次 UUID 和最终 payload。优先用文件或 stdin 传入，执行 dry-run 检查请求结构，再以 `--as user` 发起实例。

超时或回执不明时，先核对已发起列表及详情，再决定是否重试；同一次请求沿用 UUID。dry-run、附件上传成功、UUID 都不能单独证明申请已创建。

完成条件：获得实例 code 与链接并保存回执；结果不明时保持“待核验”，不另建一个申请替代。

## 5. 回读验收

按实例 code 读取详情，核对申请人、公司、账号、每行金额和日期、总额、采购申请关联、备注、附件数量及审批节点。

按上传台账把远端附件与本地文件一一对应，重新下载并核对字节数与 SHA-256；无法对应时明确待核验项，不凭数量宣称内容正确。签名下载 URL 只留在私有回执中。

名称验收与内容验收分开：若流程要求附件命名，核验远端元数据或客户端显示名称。发现名称丢失按附件参考处理。

完成条件：实例可回读，金额及附件内容匹配；名称要求也已核验，或明确报告未完成项。最终返回审批链接、单号、总额、当前状态、附件核验结果和必要取值说明。`PENDING` 表述为已提交、待审批；审批通过与打款分别以各自证据确认。
